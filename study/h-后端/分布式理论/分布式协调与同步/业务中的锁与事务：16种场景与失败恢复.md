# 业务中的锁与事务：16 种场景与失败恢复

面对一个具体业务，需要说清楚：**锁放在哪里、事务从哪里开始、在哪里提交，以及中途失败后如何恢复。**

## 先分清三个职责

- **锁**：控制谁能同时操作某个资源。
- **事务**：保证数据库内一组修改一起成功或回滚。
- **幂等、版本号、租约**：处理重复请求、旧请求和执行者失联。

锁不会自动回滚业务，事务也不会自动撤销已经发出的 HTTP 请求、Redis 操作或设备操作。

下文的 `BEGIN → COMMIT` 表示一段数据库事务。流程代码块是伪代码；SQL 中的字段、参数和冲突处理语法应按实际数据库调整。业务校验失败时，应回滚并结束当前事务，不能继续执行后续步骤。

## 1. 单字段累加：浏览量、用量、余额增量

能用一条 SQL 表达，就优先让数据库原子更新：

```text
收到增量
→ UPDATE usage SET total = total + 本次增量 WHERE id = 指定对象
→ 完成
```

不要先读到应用里算，再覆盖：

```text
读出 100 → 应用计算 110 → 写回 110
```

两个请求都读到 100 时，就可能丢失其中一次增量。

单条 `UPDATE` 本身也在事务中执行；通常不需要 Redis 锁。原子累加解决并发丢失更新，但如果同一笔增量可能重复投递，仍需要第 6 节的幂等控制。

## 2. 有条件扣减：库存、额度、余额

```text
校验本次数量为合法正数

BEGIN
→ UPDATE quota
     SET remaining = remaining - 本次数量
     WHERE id = 指定对象
       AND remaining >= 本次数量
→ 检查影响行数
    1 行：扣减成功，继续
    0 行：额度不足或对象不存在，回滚并返回
→ 写业务记录
COMMIT
```

**条件检查和扣减在同一条 SQL 里完成。** 不要先查询“够不够”，随后无条件扣减。

扣减和业务记录属于同一事务，写业务记录失败时，扣减也应回滚。如果请求可能重复，还需要幂等控制。

## 3. 复杂的读取后修改：订单状态、多个字段联合判断

```text
BEGIN
→ SELECT 订单 FOR UPDATE
→ 检查订单是否存在、当前状态是否允许操作
→ 计算并更新订单
→ 写相关数据库记录
COMMIT，释放行锁
```

竞争者等待锁，获得锁后按数据库的隔离级别读取并重新判断；如果数据库报告并发冲突，则重新执行整个事务。

适用于判断逻辑较复杂、难以直接写成一条条件 `UPDATE` 的情况。事务里尽量只放短数据库操作，避免等待用户输入或外部接口响应。

## 4. 用户编辑：防止旧页面覆盖新修改

典型场景是两个人同时编辑同一份配置。

```text
读取内容和 version=5
→ 用户在页面编辑，期间不持有数据库锁
→ 提交内容和 expectedVersion=5

BEGIN
→ UPDATE 配置
     SET 内容=新内容, version=version+1
     WHERE id=指定对象 AND version=5
→ 检查影响行数
    1 行：保存成功
    0 行：对象不存在或版本已变化，回滚并返回冲突
COMMIT
```

这是乐观并发控制。**不要从打开编辑页到点击保存一直持有锁。**

所有修改入口都需要遵守版本递增和条件更新规则。冲突后应重新读取，让用户决定如何合并，不能自动拿旧内容覆盖新版本。

## 5. 多行必须一起变化：转账、资源迁移

```text
BEGIN
→ 按固定顺序锁住相关行，例如按账户 ID 从小到大
→ 检查余额和业务条件
→ 扣减 A
→ 增加 B
→ 写流水
COMMIT
```

固定加锁顺序可以减少死锁，各条业务路径应遵守同一个顺序。

发生死锁时，数据库会中止其中一个事务。应用通常需要有限次数地重试**整个事务**，重新读取并判断状态，而不是只重试最后一条 SQL。事务重试范围内不要夹带不可回滚的外部操作。

## 6. 重复提交：支付回调、创建订单、消息重投

```text
请求携带稳定的 operationId

BEGIN
→ 尝试插入 operationId，数据库有唯一约束
→ 首次插入成功：执行业务，保存结果
→ operationId 已存在：
    检查是否同一个请求
    相同请求：返回已有结果或处理中状态
    不同请求：拒绝复用该 operationId
COMMIT
```

关键是：**重试要使用同一个 operationId。** 幂等记录还应绑定业务范围、调用者和关键请求参数，避免不同操作误用同一个键。

具体实现要使用数据库支持的冲突处理方式，例如 `ON CONFLICT DO NOTHING` 后读取已有记录。不要假设捕获唯一约束异常后，当前事务在所有数据库中都能直接继续执行。

纯数据库业务可以把幂等记录、业务修改和结果放在同一个事务里。涉及外部服务时，应结合第 12 节的持久化操作状态。

Redis 锁只能减少同时执行，不能防止“第一次执行结束、锁释放后，又来了一次重复请求”。长期防重复需要持久化幂等记录，并明确记录的保留周期。

## 7. “不存在才创建”：首次初始化、唯一资源

```text
BEGIN
→ INSERT ... ON CONFLICT ...
→ 根据插入结果决定返回新记录或读取已有记录
COMMIT
```

不要只依赖：

```text
SELECT 没查到
→ INSERT
```

两个 worker 可能同时查不到。并且 `FOR UPDATE` 不能作为跨数据库通用的“锁住尚不存在记录”的保证；部分数据库会在特定条件下使用间隙锁，行为取决于索引、隔离级别和查询形式。

最终唯一性应由数据库唯一约束保证。复杂的创建流程可以再配合数据库提供的 advisory 锁，但所有参与者必须使用一致的锁键和协议。

## 8. 多 worker 领取任务：渠道同步通知

```text
BEGIN
→ SELECT 可领取任务
     FOR UPDATE SKIP LOCKED
     LIMIT 100
→ 写 owner、执行代次、租约到期时间、尝试次数
COMMIT

→ 在事务外处理任务

BEGIN
→ 通过条件更新校验 owner、执行代次和租约仍有效
→ 标记完成；条件不满足则拒绝旧执行者提交
COMMIT
```

领取时用行锁；处理时靠租约。租约校验与状态修改必须放在同一个受保护的数据库操作中，不能先在应用中检查，再无条件更新。

worker 崩溃后，租约过期，其他 worker 可以重新领取。因此任务处理需要支持重复执行。耗时任务还需要续期；旧 worker 的外部副作用不能仅靠“完成标记校验”消除。

## 9. 多 worker 竞争同一个后台操作：缓存重建、定时同步

```text
生成本次唯一 token
→ Redis SET key token NX PX TTL
→ 失败：跳过或延迟重试
→ 成功：
    再次检查是否仍需要处理
    执行业务
    必要时通过短事务保存结果
→ finally：原子校验 token 后释放锁
```

取得锁后再次检查，是因为前一个执行者可能刚完成工作。

续期和释放都必须原子校验 token，避免删除或续期另一个执行者的锁。基本加锁、安全释放方式及其适用前提可参考 [Redis 官方分布式锁文档](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)。

租约只能在有效期及其系统假设内提供协调。对于不能容忍重复写入的业务，还需要资源端的执行代次校验，不能把 Redis 锁当作最终数据约束。

## 10. 长任务可能超过锁有效期：报表生成、大批量同步

```text
取得租约和单调递增的执行代次 epoch
→ 执行过程中定期续期
→ 每次写入结果：
    由资源端校验 owner / epoch 是否仍被允许写入
→ 完成后释放
```

如果续期失败：

```text
停止继续调度后续工作
→ 后续写入必须通过执行身份检查
→ 旧执行者不能覆盖新执行者结果
```

**TTL 到期不会停止旧进程。** 严格保护写入时，需要由资源端验证执行代次，并把校验与写入作为不可分割的操作；仅在应用里检查一下 Redis 锁，检查后仍存在竞争窗口。

随机 token 用于识别锁的持有者；单调递增的执行代次用于识别新旧执行者，两者职责不同。对于不支持执行代次校验的外部接口，还需要幂等键、去重或业务补偿。

## 11. 数据库修改后必须通知：Outbox

例如“配置保存成功，必须触发设备同步”。

```text
BEGIN
→ 保存目标配置
→ 写入待发送通知
COMMIT

后台消费者：
→ 领取通知
→ 发布消息或触发调度
→ 成功后标记已发送
```

配置和通知记录需要处于同一个数据库事务，避免两种不完整状态：

```text
配置保存成功 → 进程崩溃 → 通知没有发出
通知已经发出 → 数据库回滚 → 消费者找不到对应配置
```

发送成功后、标记完成前也可能崩溃，所以消息可能重复，消费者仍需幂等。

Outbox 保证待处理事件有持久化记录。若下游使用不持久化的通知通道，发布成功不等于目标已执行；需要按业务要求保留目标状态、重试或对账机制。

## 12. 调用外部接口或设备：支付、发邮件、Runtime 切换

```text
短事务 1：
→ 保存操作 ID、目标、处理中状态
→ 提交

事务外：
→ 使用操作 ID 调用外部服务

短事务 2：
→ 校验操作身份和当前状态
→ 保存成功、失败或结果未知
→ 提交
```

**超时不代表对方没有执行。**

超时后优先按操作 ID 查询结果，或使用对方提供的幂等接口重试。外部系统不支持幂等时，需要业务补偿或人工核对。

进程也可能在第一次提交后、发出调用前崩溃，因此处理中操作需要后台恢复机制。第二次提交失败时，也应依靠同一个操作 ID 查询确认，不能盲目再执行一次。

不要因为数据库回滚，就认为邮件、付款或设备变更也被撤销了。

## 13. 多步骤跨系统操作：扣款后发货、创建云资源后登记

```text
记录流程与每一步状态
→ 执行步骤 A
→ 记录 A 的结果
→ 执行步骤 B
→ B 失败：
    重试 B
    或执行 A 对应的补偿操作
→ 记录最终状态
```

这类流程通常靠持久化状态机和补偿推进。

每一步都可能在“外部操作成功、状态记录之前”崩溃，因此各步骤也要有稳定操作 ID，并支持幂等执行或结果查询。

补偿本身也是新操作，可能失败，需要幂等和重试。例如退款不是把已经发生的扣款“数据库回滚”。无法自动补偿的状态需要保留证据，并进入可核对、可人工处理的流程。

## 14. 数据库与缓存一致性：修改配置后刷新 Redis

常见的缓存旁路流程：

```text
BEGIN
→ 更新数据库
COMMIT
→ 删除对应缓存
```

删除失败需要重试；要求可靠时，可以在数据库事务内写入缓存失效通知，由后台处理。

需要注意：

- 数据库回滚不会回滚 Redis。
- 更新后删缓存仍可能遇到并发读回填旧值。
- 对一致性要求高的数据，应结合版本号、可靠失效机制，或者直接读取数据库。

并发回填的一个例子：

```text
读请求查到旧数据库值，尚未写缓存
→ 写请求更新数据库并删除缓存
→ 读请求把刚才读到的旧值写回缓存
```

Redis 锁只有在相关读写路径都遵守协议、并正确处理租约过期时，才能提供相应保护。可靠失效通知解决“删除动作丢失”，不自动解决所有并发回填问题。

## 15. 文件编辑与保存：ifMatch

```text
读取文件内容和哈希
→ 用户编辑
→ 保存时重新检查当前哈希
→ 不一致：返回冲突
→ 一致：写入新文件
```

需要区分两件事：

- 临时文件写完后原子替换：避免读到半个文件。
- 将“检查版本和写入”统一保护：避免并发覆盖。

原子替换本身不能防止丢失更新。进程内锁也无法阻止外部编辑器修改文件。

如果多个写入者都受同一服务管理，可以在同一个临界区内完成检查和替换；如果允许外部进程直接写文件，就需要所有写入者共同遵守协调协议，或使用提供条件写入能力的存储。普通文件系统上的“检查哈希后 rename”本身不是内容版本的原子比较并交换。

## 16. 单进程内部共享状态：Connector 的内存对象

```text
取得 asyncio.Lock
→ 读取和修改共享状态
→ 释放锁
```

`asyncio.Lock` 用于同一事件循环中的协程协调，不是线程锁或跨进程锁。启动多个进程后，各自拥有自己的锁。

如果被保护的状态在数据库中，需要使用数据库并发控制；如果资源跨进程共享，则需要跨进程协调机制。

锁保护了临界区，也不意味着临界区内的修改会自动回滚。中途异常时，仍需明确内存状态是否已经部分改变，以及如何恢复。

## 如何选择方案

| 业务问题 | 优先考虑 |
| --- | --- |
| 一条 SQL 能完成修改 | 原子 UPDATE、条件 UPDATE |
| 多条数据库修改必须一起成功 | 数据库事务 |
| 需要读取最新数据再做复杂修改 | 短事务 + 行锁 |
| 防止旧页面覆盖新数据 | 版本号条件更新 |
| 防止重复请求造成重复效果 | 幂等键 + 唯一约束 |
| 多 worker 分摊数据库任务 | SKIP LOCKED + 租约 |
| 多 worker 协调后台工作 | Redis 租约锁，必要时加执行代次 |
| 数据保存后必须发消息 | Outbox |
| 外部接口超时、结果未知 | 操作 ID + 查询确认 + 幂等重试 |
| 跨系统多步骤失败 | 持久化流程 + 补偿 |

## 用三个失败点检查设计

设计每一条流程时，再检查：

1. **提交前崩溃**：数据库修改是否回滚？是否已经产生外部副作用？
2. **提交后崩溃**：哪些工作尚未完成？由谁从持久化状态中发现并恢复？
3. **外部操作成功但响应丢失**：能否查询结果？重试是否会重复扣款、发信或修改设备？

能明确说明这三种情况下如何恢复，锁和事务的边界通常就比较清楚了。
